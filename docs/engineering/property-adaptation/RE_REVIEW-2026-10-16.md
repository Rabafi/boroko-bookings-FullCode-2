## F2 — P2: archived unresolved operations have no operator recovery journey

Locations: `Settings.jsx` archivePending around line 752; `src/shared/propertyTransitionOperation.js` archiveAndSupersede around line 1182; controller checkOutcome resolves the current pending operation.

The UI says the superseded operation remains recoverable via Check outcome, but after archiveAndSupersede the current stored operation is cleared. Settings does not offer an archive list/selector or import listArchivedTransitionOps. Check outcome then addresses only the new current pending operation (or reports none), and restarting restores only the live storage key. An unresolved old key is retained in raw local storage but has no supported operator path to check its late result. Existing tests prove archive retention, not that an operator can recover it.

Required correction: expose a scoped read-only archive/history recovery path for unresolved operations and check status by their original key; distinguish superseded-but-unresolved from authoritatively completed/cancelled outcomes. Do not resubmit an archived operation implicitly or clear another current operation when an old status finishes. Alternatively, keep unresolved operations in a recoverable active collection until an authoritative terminal result exists. Remove unsupported claims of a recovery path until it actually exists. Record actual operator actions rather than unconditionally asserting that an outcome was checked in the archive reason.

Required tests: timeout, archive-and-supersede, begin another change, reopen/restart, select the original operation and query its late outcome. Confirm property/user isolation and that the second operation is untouched. Mount production Settings for this journey.
